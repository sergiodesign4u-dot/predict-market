Why it is not a variant of input

input.css already carries the product's field face and this file reads none of it, which is a claim that needs a reason rather than a shrug. Three of them, and each is anatomy rather than taste.

the differencewhy it is anatomy
the mark is INSIDE the control.amount-cur is a SIBLING of the field, because a currency mark is not part of the value: input.css argued that out and moved the $ out of the input's own value to get the keyboard right. A magnifier is the opposite. It is not a value at all, it says what the box IS, and it sits inside it the way a placeholder does
the value is a QUERY, not a quantityevery declaration in input.css that is about the value is about a number: the display face, --text-18 and --text-30, inputmode="decimal", the spin buttons stripped, the mono figure. This field holds words in the body face at reading size, and it is the only field in this product that does
it carries a control of its owna field a person can empty needs something to empty it with. No other field here does, because a bet amount is replaced rather than cleared, so .search-clear is a STATE the input family has no vocabulary for: it exists only when the field has a value

What it does share it shares through the system and not through a copy: the --bg-well ground, --border-field, the 44px floor from base.css, and the two-question focus input.css argued for (:focus says the field is active however you got there, :focus-visible draws the ring for a keyboard). Those are the same because they are read from the same roles, which is what a token system is for.

Empty, holding a query, and holding one that matches nothing. The third differs from the second in the count and in nothing else, which is the point: the field does not turn red when a search fails, because a search that finds nothing is not an error and the product has no error tone to spend on it anyway. The block that says what to do next is state-block, drawn under the count.

The clear button is not in the markup when the field is empty. A control that clears an empty field is a 44px target that does nothing, so the page script adds and removes it with the value. The stylesheet also carries .search-field:has(.search-input:placeholder-shown) .search-clear{display:none}, which is not the mechanism: it is what makes a stale one harmless if a screen is ever drawn with the button and no value in it. :placeholder-shown is the one state selector that reads the VALUE.

type="search" is the role, and the decoration is the price

The type is what makes this a searchbox in the accessibility tree instead of a plain textbox, which is the whole reason it is not type="text". Both engines draw furniture on it for free: WebKit gives it a rounded UA field and its own cancel button, Chromium gives it a cancel button too. The component draws its own clear control, at 44px and in the system's ink, so both UA versions come off by name (::-webkit-search-cancel-button, ::-webkit-search-decoration) rather than by hoping appearance:none reaches them.

This is the same shape as the amount field's type="number" lesson, read from the other end. There the type was right for a phone keyboard and wrong for a locale, and the fix was to take the mark out of the value. Here the type is right for the accessibility tree and wrong for the drawing, and the fix is to take the drawing off. A type is never only semantics.

What this component re-opens

Search is not missing from this product, it was DECIDED against, and the decision is conditional. ia/docs/sitemap.md: "Search - Deferred until catalog scale. At 10-20 curated markets, users scan the Event Feed; they do not search. Search does not close a confirmed job at this scale. When added, it attaches to the Events tab under FJ1 - not a bottom slot."

Measured 2026-08-16: the product draws 25 distinct events, counted from every .q and .ed-q in the painted tree. So the deferral's premise has moved from 10-20 to 25 and has not been overturned by scale. The 1,284 the critique cites is the resolved-on-chain trust figure in the footer strip, not the browsable catalog, and the two count different things.

What the deferral did not answer is the one the critique got right: there is no route to an event except scrolling a category, and the 404 draws a magnifier over "This page does not exist" while ia/docs/pages/system.md names its two escapes as "search or quick links". The product had been drawing the icon for a control it did not have.

The IA's own placement is honoured: the field lives on the Events destination and search takes no bottom-nav slot. The way in from the other 102 screens is a header utility, beside the bell and the favourites mark, which is where the product already puts a thing that is not a destination.

The rule

A filter narrows a list you are browsing; a search finds a thing you already have in mind. That is why the field is not in the feed head beside Sort and How often: the critique's own finding about that head is that it already carries two category selectors using the same five words, and a third control doing a fourth job would be worse than the defect it fixed.

The count is mono because it is a figure a person reads twice, before and after typing, and a figure that changes has to be a figure both times.

The drawn state is the static one. All three screens carry their filtered grid in the markup, with hidden on the cards that do not match, and the page script only reproduces what the file already says. A page whose state exists only after a script has run is the defect this repository paid for when eight bet panels carried a retired payout that only a script corrected.

The anti-rule

Never give search a navigation slot. The IA settled this before the control existed: four destinations, and finding a thing is not one of them.

Never colour a search that finds nothing. Zero results is an answer, not a failure, and red in this product means NO.

Never let the count be typed. It is computed from the same pass that hides the cards, so the figure and the grid under it cannot disagree.
