What it is

The control a person uses to move around the product. It is the quietest thing in the system on purpose: no ground, no edge, no corner, the width of the row it sits in. Where a button commits and a chip chooses, this one goes.

Anatomy

Which part is which, in the product's own words. Every class named here is one this file styles, and the build fails if it is not.

  • .nav-item - the atom, and it is four declarations: full width, transparent, no border, no corner. Everything else belongs to a face. It is an <a> where the slot navigates and a <button> where it opens the sign-in sheet, which is the right answer to both and is what ui-kit/docs/defects.md row 78 settled on 2026-08-07: until then the navigating one was a <button> inside an <a>, two controls in the tab order where a person can see one.
  • .nav-item.nav-slot - a mark over a label, centred, 10px, --text-muted, in the bottom bar. Its current-page state is the one thing the bar says at a glance.
  • .nav-item.nav-row - a line of a menu: full width, left aligned, 11px, --text-primary. The five in the account dropdown are <a> since 2026-08-07, which is what found the atom's missing display: width:100% does nothing to an inline box, and the <button> element had been supplying inline-block for as long as every one of these was a button.

When to use

The judgement a generator cannot read out of css, and the reason ui-kit/authored/navitem.md exists.

For anything that navigates and stands in a list, a bar or a menu. If it commits, opens or submits, it is button; if it selects among alternatives and carries a value, it is chip.

The rule, and the anti-rule

One sentence to follow and one mistake worth naming. An anti-rule has to name the component that should have been used instead, or it is a complaint rather than an address, and the build checks that it does.

Do

The current item is stated by ONE thing. In the bottom bar the ink says where you are, so the ground answers the pointer and the colour does not. If pointing at a slot pulled its label toward brass, the one signal the bar carries would be said by two different things at once, and a hover can stick after a tap on a phone, so the wrong slot would go on claiming to be current after the finger left.

The state is reached from the ancestor, and the attribute is what is named. aria-current="page" sits on the <li> in this product, so the rule is [aria-current="page"] .nav-item.nav-slot. It names the attribute alone and not the bar, because being the current item is the ATOM's state wherever the atom stands.

Every hover here is written at the face's own two-class weight. .nav-slot:hover would be (0,2,0) and would lose to the current-page rule at (0,3,0) on exactly the slot a person taps most. components/bottomnav.css bought the same weight by naming the <li>; this file buys it by naming the atom and the face together, and the press comes last at the same weight so that a tie is broken by source order.

Never

Never give one a ground at rest. The moment a nav item has a fill, a row of them reads as a row of buttons and the current one stops being the only thing standing out.

Never draw one from button. That family gives a quiet control --bg-control and a 10px corner, which is the opposite of every value here.

Seen: ui-kit/docs/atoms.md, and ui-kit/docs/backlog.md S45 and S46 for the two things this atom's arrival did not settle.

/* ============================================================================
   THE SECOND ATOM TO GET A FILE, 2026-08-06, and the first one that did not
   have one at all. `ui-kit/docs/atoms.md` defines this atom as **a thing a
   person taps that GOES somewhere and that draws NOTHING until it is pointed
   at**: transparent, no edge, no corner, as wide as the row it sits in. Two
   kinds measure exactly that and they came here from two files.

     the bottom nav slot          420 placements, components/bottomnav.css
     a row of the account menu    365 placements, components/header.css

   MEASURED AT REST, AT 1440 AND AT 380, BOTH THEMES: transparent ground, 0px
   border, 0px corner, full width, and a press on --bg-pressed. Every one of
   those agrees. What differs is a direction, a size, an ink and an alignment,
   which are modifiers, so this is one atom with two faces and the shared line
   is written once at the top instead of twice in two regions.

   THE THIRD KIND OF THIS ATOM IS NOT HERE AND THAT IS DELIBERATE. A
   sub-category row, `.subcat button`, 234 placements, measures as a hairline
   PILL at 380 and a 10px full-width row above 860: a 1px edge and a corner at
   both widths, which is neither this atom's rest face nor one modifier away
   from it. It was moved out of `chip` on the strength of the desktop rule
   alone, which is the same half-measurement that put the social mark in the
   wrong atom. `ui-kit/docs/backlog.md` S46 holds it, with both widths written
   down.

   AND SO IS A NOTIFICATION ROW. `.notif-drop li a` shares three declarations
   with the account row today, in the same file, under a different name: the
   ink, the hover and the press are one selector each. It is the same control
   with a different content, and it stays in components/header.css this pass
   for two measured reasons rather than an opinion: it is `display:block` where
   the account row was then the button default `inline-block`, and its own
   font-size is the browser's 16 where the account row is 11. Neither draws
   anything, and neither is a value this pass is entitled to choose. S46 again.
   (The display half of that stopped being true on 2026-08-07: the account row
   became an `<a>`, the element's default went with it, and the atom declares
   `display:block` for both now. The paragraph is kept as it was written because
   it is the reasoning of the day, and the correction is here rather than in a
   rewrite of it.)

   WHAT THE TWO REGIONS KEEP is what a region is allowed to keep: where the
   control sits. `components/bottomnav.css` keeps the bar, its sticky position,
   the groove along its top edge, the list, the dividing rules between slots and
   `text-align:center` on the <li>. `components/header.css` keeps the dropdown
   panel, its shadow, its corner and where it opens. Neither says what the
   control inside it looks like any more.
   ============================================================================ */

/* The whole atom, and it really is this short: it is the ABSENCE of a control
   until a pointer arrives. `border:0` rather than `border:none` because that is
   what both files said; both compute to a 0px none border either way. */
/* `display:block` arrived on 2026-08-07 and it is the fourth value this atom had
   been WEARING without writing down. `width:100%` is the whole reason this class
   exists as a row, and width does nothing to an inline box: the <button> element
   was supplying `inline-block` for free, so the declaration worked for as long as
   every one of these was a button and stopped the moment the account dropdown's
   365 became links. Measured: 194x33 to 66x30, the row collapsing to its own text.
   The two faces that had already become anchors each declared a display of their
   own - `.nav-slot` flex, `.nav-row-stack` block - which is exactly why the gap
   stayed invisible until a face that declared none crossed over. */
.nav-item{display:block;width:100%;background:transparent;border:0;border-radius:0;cursor:pointer;text-decoration:none}

/* --------------------------------------------------------- the slot face ---
   A mark over a label, in a bar that is the only navigation a phone has. Its
   ink is the current-tab signal and NOTHING else, muted against brass, which is
   why the ground answers the pointer here and the colour does not: if pointing
   at a slot pulled its label toward brass, the one thing the bar says at a
   glance would be said by two different things, and a hover can stick after a
   tap on a phone, so the wrong slot would go on claiming to be current. */
.nav-slot{display:flex;flex-direction:column;align-items:center;gap:var(--space-4);padding:var(--space-8) var(--space-4);font-size:var(--text-10);color:var(--text-muted)}
.nav-slot .ic{width:var(--size-20);height:var(--size-20)}
.nav-slot .ic:has(use){color:var(--text-muted)}
/* `aria-current` sits on the <li>, not on the control, so the state is reached
   from an ancestor. It is written with the attribute alone rather than with the
   bar's class, because being the current item is the ATOM's state wherever the
   atom stands, and naming `.bottom-nav` here would be this file holding a
   region's name. */
[aria-current="page"] .nav-item.nav-slot{background:transparent;color:var(--text-brass);font-weight:var(--weight-bold)}
[aria-current="page"] .nav-slot .ic{stroke:var(--text-brass)}
[aria-current="page"] .nav-slot .ic:has(use){color:var(--text-brass)}

/* ---------------------------------------------------------- the row face ---
   A line of a menu that drops out of the header. Full width, left aligned, the
   strong ink because a menu is read rather than glanced at, and a brass wash
   under the pointer rather than the neutral one the bar uses. */
.nav-row{padding:var(--space-8) var(--space-8);font-size:var(--text-11);color:var(--text-primary);text-align:left}
/* AND THE NOTIFICATION ROW JOINED IT ON 2026-08-06, which is what S46 asked for.
   It is the account row with a different content: same transparent ground, same
   8/8, same --text-primary, same brass wash, same press, and the three of those
   were literally one selector each in components/header.css - written once for
   both controls and split when the account row left. Two values had held it back
   and both were measured to draw nothing. Its font-size was the browser's 16
   where the account row is 11, and NOTHING in it reads a font size: the row holds
   a <strong> and a <span>, both display:block with sizes of their own, and no
   bare text node between them. So it takes the row's 11 and no glyph moves.
   THE ONE VALUE THAT DOES DRAW IS THE DISPLAY, and it gets a modifier rather than
   an argument. A menu row is one line and was the button default, inline-block; a
   notification is a title and a detail under it, so it is a block.
   AND ON 2026-08-07 THE ARGUMENT CHANGED SIDES, which is worth leaving visible.
   The account row became an `<a>`, whose default is `inline`, and `width:100%` does
   nothing to an inline box: the row collapsed from 194x33 to 66x30. So the atom
   declares `display:block` now and this modifier is what it always was, the name
   for a row that stacks. Nothing moved when it arrived, because block and
   inline-block draw the same box for an element that is already full width in a
   list of its own.
   The title and the detail stay in components/header.css: they are the row's
   CONTENT and not the control's face, the same way a card keeps its own title. */
.nav-row.nav-row-stack{display:block}

/* ------------------------------------------------- and here is the finding ---
   THE TWO FACES ANSWER THE POINTER DIFFERENTLY AND AGREE ON THE PRESS, which is
   now the third time an atom has come out that shape: the icon button's six
   faces, the tile against the social mark, and these two. A quiet neutral wash
   on the bar, 420 placements; the brass wash the rest of the header uses, 365.
   Neither is a majority and both have an argument, so both are kept and
   `ui-kit/docs/backlog.md` S45 is where the question lives.
   THE ORDER OF THESE FOUR RULES IS LOAD BEARING. Each hover is written at the
   face's own two-class weight so that it can reach the slot a person is
   standing on: at `.nav-slot:hover` it would be (0,2,0) and would die under the
   current-page rule above, which is (0,3,0), on exactly the tab that gets
   tapped most. That was true in components/bottomnav.css too, where the rule
   named the <li> to buy the same weight, and the note there explains it. The
   press is last and at the same weight as the hovers, so a tie is broken by
   source order and a held control shows the press rather than the hover. */
.nav-item.nav-slot:hover{background:var(--tint-hover)}
