Card grid

A fluid track of event cards, one column to four, with no media query at all. auto-fit over minmax(min(100%, 300px), 1fr), so the column count is arithmetic on the available width rather than a set of breakpoints somebody has to keep in step with the card.

Live

Cut out of event-feed.html byte for byte, with the ancestor chain it has there, and painted by components/index.css alone. Every string is the shipped microcopy, because none of it was retyped. The feed, which is where the track was read from. Trimmed to the first four cards of twelve so the frame stays readable; nothing else is changed, and four is enough to show the track step from one column to two to three.

This is the only place the pattern exists outside the product. A component has a specimen as well as a stand; a pattern has neither, because step 3 took patterns out of gate 24's corpus deliberately: that gate compares what a component contains against what it contains on the screens, and a pattern contains whatever the screen puts in it. So this frame is not an illustration of the pattern, it is the test of it.

Anatomy

What each part is and whose it is. A part that belongs to a component links to that component's page, because the answer to "how does this look" is there and not here: this file decides placement and nothing else.

Everything inside, read from the markup: card (.card), yesno (.yesno), iconbtn (.icon-btn), options (.options). The class in brackets is what put each component in the list, through the same ownership map that computes the level and orders the cascade. A name here that surprises you is worth following: a class declared in the wrong file makes a pattern read as holding a component it has never seen.

Variants

No variants. The pattern has one arrangement, and a screen that needs a different one needs a different pattern.

What it composes

The COMPONENTS in it, named by a person. The Anatomy above answers which class is which; this answers what each part contributes, which is the question a class list cannot reach.

  • card - the item. Its photograph, its question, its probability and its why are all its own; this pattern decides only how many of them fit across.
  • yesno - the pair inside a binary card, which is the control the track has to leave room for at the narrowest column.
  • options - the two option rows inside a multi-outcome card, capped at two so a multi card stays close to a binary card's height and the meta rows line up across the track.

When to use it

When a screen lists things of one kind and the number of them is decided by the data, and the items are the same shape, so a track that reflows beats a layout authored per width.

Once per screen. Two grids on one page means two different sets of one kind, which is a question about the screen rather than about the track.

By hand: when the items are not the same shape. A row of three blocks that happen to sit side by side - a summary, a chart and a note - is a flex row with its own sizes, and putting it in this track would let a narrow window stack them in an order nobody chose. The test is whether an item could be the first, the last or the only one without looking wrong.

The rule

One grid per screen, and the column count is arithmetic: no breakpoint in this file, so a card that changes its minimum width changes the track by itself and nothing has to be edited in two places.

The anti-rule

Never let a bet control into it. A screen that carries this track has no amount field and no Confirm on it: a card's YES / NO belongs to yesno and routes to the detail with the side pre-selected, while the thing that commits money is betpanel, which R3 keeps to one per screen and R7 keeps off every screen with a grid.

Seen: wireframes/_conventions.md S3 states it as a decision that had to be written into the grey tree's contract - "a tap routes to Event Detail with the side ... pre-selected. It does NOT place a bet on the card and does not bypass Event Detail" - which is a sentence written because the alternative was on the table. R7's counter is what confirms it held: 23 screens with a grid, 0 with a panel or a dock.

What it arranges, and whose the states are

auto-fit over minmax(min(100%, 300px), 1fr) with one gap, at every width. The min(100%, 300px) is what stops a 300px minimum from overflowing a 360px phone, and it is the reason there is no media query: below one column's worth of room the track takes the full width instead of scrolling sideways.

No states of its own. Everything in the track that answers a pointer is a card, and the whole-card hover, the question link and the save control are photographed on that component's page.

The file

A pattern loads LAST in components/index.css, after every component, because it has to be able to place what it holds. It carries no colour at all, and gate 23 fails the build if one appears.

components/patterns/card-grid.css
/* components/patterns/card-grid.css
   Pattern: the card grid. A fluid track of event cards, one column to four.

   Assembled from: card. One brick, many of it, which is still a composition:
     what the pattern decides is the track, and the card decides nothing about
     where it stands.
   Stands on: 23 ui-visual screens, exactly the ones that list events
     (event-feed x21 across the four categories and their states, favorites x2).
     Counted from the markup and not by grep: `grid` also matches .grid-l, the
     chart's grid line, on 9 more screens, and .hf-grid on one. Those are not
     this. 23 elements on 23 screens, one grid per screen.
   Moved here from: components/feed.css, three rules, cut and not copied.
   Colour goes through a role, geometry straight from a primitive. No em dash. */

.grid{display:grid}
/* WHAT THE !important WAS ARGUING WITH. Four rules used to sit beside this one:
   three breakpoints stepping the grid 2 - 3 - 4 columns, and a category variant
   at auto-fill 240px. All four were already dead. The three breakpoints lose to
   the auto-fit rule below on source order alone, and the category variant was
   outranked only by the !important that rule carried. So the shipped grid has
   always been the one rule, and the shout was holding a cascade nobody had
   cleaned up. Deleting the four is what made the !important removable without
   moving a card: a fluid auto-fit track needs no breakpoints, which is also why
   this pattern has no media query of its own. */
.grid{align-items:stretch;grid-template-columns:repeat(auto-fit,minmax(min(100%,300px),1fr))}
.grid{gap:var(--space-16)}
